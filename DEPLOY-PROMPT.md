A zero-dependency Node 22 app (no npm install; plain `node`). It scores live
Open-Meteo weather across the vetted nomad cities (currently 109), has a capped AI API
call write a "best place to be right now" verdict, plans Tesla road trips
(OSRM + supercharger data), and serves a single-page frontend. Source is on
Charles's Mac at `/Users/charles/Projects/sunchaser` (git repo, deploy from
`main` HEAD).

## What to copy

Everything except: `.git/`, `var/` (runtime state, created on boot), `.env`
(local secrets), `*.md` handoff docs if you prefer. The app expects this
layout intact relative to its root: `engine/`, `server/`, `public/`,
`data/`, `tools/`, `cli.js`. Suggested target: `/var/www/sunchaser/`.

## Service

- Run: `node server/index.js`. Binds `127.0.0.1`, port from `PORT` env
  (default 3005; ports 3002-3004 are taken by cheap-proxy, tutor-proxy, and
  lotcheck; pick the next free one per your registry and set `PORT`
  accordingly).
- Working directory must be the app root: it reads `data/` and writes
  runtime state to `./var/` (raw weather cache, scored snapshot, verdict,
  spend counters, route cache). The service user needs write access to
  `./var/` only. Nothing else is written anywhere.
- Logs to stdout/stderr; journal is fine.

## Scheduled refresh (systemd timer)

The web server refreshes weather lazily, but the AI verdict is only
generated by the CLI. Add a oneshot service + timer, hourly:

- Service: `node cli.js verdict` in the app root, same user, with
  `EnvironmentFile=/etc/sunchaser.env`.
- Behavior: refreshes weather (batched, tiered: active hourly, dormant
  daily; ~1,200 Open-Meteo location-calls/day total), rescores, and
  regenerates the verdict only when the data changed (content-hash cache).
  24 runs/day sits under the 40/day cap with headroom for manual runs and
  determinism-check retries.
- First deploy: run it once by hand so the site has data before the first
  page view.

## Caddy vhost

```
sunchaser.rockofpages.com {
    root * /var/www/sunchaser/public
    @api path /api/*
    reverse_proxy @api 127.0.0.1:<port>
    file_server
}
```

(The Node app can also serve the static files itself; the split above just
matches the lotcheck pattern. Add the DNS A record for the subdomain if
rockofpages.com isn't wildcarded.)

## Endpoints and verification

- `GET /api/health` → `{ok, snapshot_age_min, verdict_age_min,
  ai_calls_today, ai_daily_cap}`. Healthy after first timer run: all
  non-null, ages under ~200 min.
- `GET /api/snapshot` → scored cities JSON (~180 KB raw; may take ~20 s on a
  cold cache while it fetches weather, then instant).
- `GET /api/verdict` → cached AI verdict; 404 until the first CLI run.
- `GET /api/rents` → static Zillow ZORI rent tiers from `data/rents.json`
  (display-only cost chips; regenerated locally, ships with the code).
- `GET /api/route?from=Atlanta,%20GA` → trip plan JSON (calls OSRM's public
  server + Open-Meteo geocoding; throttled to 6/min per IP in-app).
- Frontend `/` should render: verdict panel, city cards, map with ~109
  dots, sortable table, route planner.

Security posture, for your review rather than action: the only outbound
calls are Open-Meteo, OSRM, geocoding-api.open-meteo.com,
api.fireworks.ai, and api.anthropic.com. No inbound endpoint triggers AI
spend; the route
endpoint is the only one doing live upstream work and it is throttled and
input-length-bounded. Static serving is separator-aware-contained to
`public/`. The code passed a two-model review (Codex + GLM 5.2) against the
rubric in `REVIEW-PROMPT.md`; 21 findings fixed, commits `7a08b62` and
`a694d68`.
